# RFC 2544: Benchmarking Methodology for Nettwork Interconnect Devices

S. Bradner and J. McQuaid, “Benchmarking Methodology for Network Interconnect Devices,” Mar. 1999, doi: 10.17487/rfc2544.

## TLDR

This Request For Comment was dense with infomration on best practices when 
designing benchmarking tests. It is definitely a must read for anyone designing
benchmarking as it describes the various mesurable device constraints 
(throughput, latency, frame loss, etc), as well as providing procedures for 
finding those measurements, and suggests formats for reporting the findings.

## 26. Benchmarking Tests

### Throughput

> "  Procedure:  Send a specific number of frames at a specific rate
   through the DUT and then count the frames that are transmitted by the
   DUT. If the count of offered frames is equal to the count of received
   frames, the fewer frames are received than were transmitted, the rate
   of the offered stream is reduced and the test is rerun"
- This feels like somewhat of a pain to setup when our Mesh devices limit the 
  ammount we can even send, I guess if we have a repeater, we could try this 
  test, but would likely need many mesh nodes (how many idk). Testing the 
  throughput of our service seems somewhat irrelevant, though I do not know..
  
### Latency

> "The time at
   which this frame is fully transmitted is recorded (timestamp A).  The
   receiver logic in the test equipment MUST recognize the tag
   information in the frame stream and record the time at which the
   tagged frame was received (timestamp B).

   The latency is timestamp B minus timestamp A"
- Simple. elegant, latency tests should be one of the first things implemented

> " The test MUST be repeated at least 20 times with the reported value
   being the average of the recorded values."
-  What makes 20 so special? I want to do 32 >.<

> "Reporting format:... The latency results SHOULD
   be reported in the format of a table with a row for each of the
   tested frame sizes."
- I prefer bar plots. Though I do wonder if increasing 'frame size' will have 
  any noticable latency impact as the frames are already limited to 150 chars 
  max (not counting header data)
- Also don't forget  the earlier requirement of at least 5 frame sizes (one 
  being max and one being min)

## Frame Loss Rate

> "The frame loss rate at each point is
   calculated using the following equation:

          ( ( input_count - output_count ) * 100 ) / input_count


   The first trial SHOULD be run for the frame rate that corresponds to
   100% of the maximum rate for the frame size on the input media.
   Repeat the procedure for the rate that corresponds to 90% of the
   maximum rate used and then for 80% of this rate.  This sequence
   SHOULD be continued (at reducing 10% intervals) until there are two
   successive trials in which no frames are lost."
- Is this as difficult as a throughput test? Can one node overwhelm another w
  with messages? If not, then we need multiple, I think reading through this 
  has me rethinking some of the test design (which is a good thing)

## Back-to-back frames

> "Procedure:  Send a burst of frames with minimum inter-frame gaps to
   the DUT and count the number of frames forwarded by the DUT.  If the
   count of transmitted frames is equal to the number of frames
   forwarded the length of the burst is increased and the test is rerun.
   If the number of forwarded frames is less than the number
   transmitted, the length of the burst is reduced and the test is
   rerun.

   The back-to-back value is the number of frames in the longest burst
   that the DUT will handle without the loss of any frames.  The trial
   length MUST be at least 2 seconds and SHOULD be repeated at least 50
   times with the average of the recorded values being reported."
 - This feels like an important thing to know about mesh-nodes for implementing
   our app. Concern a test like this addresses: "what if our gateway node 
   over burdens the access node at a rate which it cannot process"? Is that 
   likely, I don't think so, but I'm happy to test it to know for certain.
